# SiteNova Connect — Local Self-Hosted InsForge Setup

This guide is for local development on your own computer. It does not modify either of your existing Supabase projects.

## 1. Prerequisites

- Docker Desktop with Docker Compose v2 (Windows/macOS) or Docker Engine + Compose v2 (Linux).
- Git.
- Node.js 20+.
- At least 4 GB RAM available to Docker as an initial minimum; 8 GB or more is more comfortable.
- Enough free disk space for Docker images, PostgreSQL data, logs and uploaded media.

InsForge is a separate backend platform. Its official self-hosted quickstart uses Docker Compose and creates its own PostgreSQL volume, secrets and local services.

## 2. Install InsForge in a dedicated directory

Open a terminal. Inspect the official setup script before executing it; do not pipe an unreviewed script directly into a privileged shell.

```bash
mkdir -p ~/sitenova-infrastructure
curl -fsSL https://raw.githubusercontent.com/InsForge/InsForge/main/deploy/setup.sh -o /tmp/insforge-setup.sh
less /tmp/insforge-setup.sh
sh /tmp/insforge-setup.sh ~/sitenova-infrastructure/insforge
cd ~/sitenova-infrastructure/insforge
```

The official setup helper downloads the Compose stack files and creates a private `.env` with generated secrets. It does not start the containers.

Open the generated `.env` and confirm the generated values are unique. Do not commit this file.

For a single local instance, retain the default project name and ports unless they conflict with other software. If ports conflict, choose a unique `COMPOSE_PROJECT_NAME` and unused ports. Never run two different InsForge directories with the same Compose project name because they can adopt the same containers and volumes.

Set browser-facing URLs for local development, following the current official InsForge README instructions. Then start:

```bash
docker compose up -d
docker compose ps
docker compose logs -f --tail=100
```

Open the local InsForge dashboard at `http://localhost:7130` (unless you changed APP_PORT). Complete the initial admin setup and save the generated project credentials in a password manager.

## 3. Verify isolation and health

- Confirm the InsForge containers and database volume are named for this dedicated installation.
- Confirm the database is not reachable from the public internet.
- Confirm only the intended local app/API ports are exposed.
- Confirm the two existing managed Supabase projects are not configured as endpoints or referenced by any environment variables.
- Create a disposable test table and test Auth / Storage before importing any WACRM schema.
- Do not import customer data at this stage.

## 4. Configure SiteNova Connect

Copy the application environment template:

```bash
cd <path-to-your-wacrm-clone>/sitenova-connect
cp .env.example .env
```

Set the local InsForge base URL and credentials in `.env`. Use only the keys generated by this local instance. The InsForge SDK/client must be configured from the official docs matching the installed InsForge release. Never place the root admin password, database password, JWT secret, encryption key or server/admin API key in browser code.

## 5. Run the application

```bash
npm install
npm run check
npm run dev
```

Open `http://localhost:3000`. The current SiteNova Connect UI is a scaffold; feature modules and the InsForge data adapter are still to be ported and tested.

## 6. Stop and restart

```bash
docker compose stop
docker compose start
```

To remove containers without deleting persistent data, use `docker compose down`. Do not use `docker compose down -v` unless you intentionally want to destroy this InsForge instance's volumes and have verified backups.

## 7. Before production

Local Docker is for development, not production availability. A production deployment needs a dedicated always-on host, domain, HTTPS, firewall, backups, monitoring, SMTP, object-storage strategy, secret rotation, update/rollback plan and tested recovery. Do not expose Studio, PostgreSQL or internal services publicly.
